【产品经理】

- 交付范围：代码 + README + LICENSE + 文档四件套（设计.md/框架.txt/使用说明.md/codex.txt）+ git init 首次提交；
  推送 GitHub 单独确认（需要凭证或仓库已存在）。

【调研：GitHub 类似工程】
- Misaka-blog/argo-script：CloudFlare Argo Tunnel 一键管理脚本。同为菜单式 bash 管理器，
  偏“装 tunnel + 配 ingress”，不带 Token 多入口表管理。
- cloudflare/cloudflared：官方客户端，底层依赖，非同类。
- fscarmen/ArgoX、yonggekkk/argosbx、eooce/Argo：Argo + Xray/sing-box 代理隧道，定位不同
  （跑 VLESS/VMess 代理协议）。
- 各类“远程托管固定隧道脚本”博客方案：调用 Zero Trust API 自动建隧道，多为单次脚本。
结论：**纯 cloudflared 隧道菜单管理器 + Token 模式 + 多 ingress 入口表 + systemd/OpenRC 双 init + 健康检查**
这个组合，GitHub 上没有现成等价物，值得独立成工程。

【用户需求】
原文：「也要支持一条命令就从github进行安装使用，并且，你可以写个一整行的命令。我直接写上需要的参数，
直接就能安装上。」
即：① 支持从 GitHub 一行命令安装；② 该行命令里直接写好参数，装完即完成配置。
（与第一轮"保持 install.sh、不做 launch.sh"的决策相反，以最新需求为准。）

【产品经理】
- 提供两个层次：不带参数 = 装完进菜单（照顾新手）；带参数 = 装完自动配好并启动（照顾批量/自动化）。
- 参数集合对齐现有隧道配置：target / mode / token / hostname / path / protocol，外加 --no-start。
- 必须支持离线（目标机可能出不了网）与完整性校验（走公网分发脚本必须防篡改）。
- 明确提示 --token 会进 shell 历史，并给出 YJL_ARGO_TOKEN 环境变量替代方案。

【首席架构师】
- 一行入口单独成文件 launch.sh，与主程序解耦；安装环节复用 install.sh，不重复实现安装逻辑。
- 「带参数直接配好」的逻辑放进主程序 yjl-argo.sh 的 `configure` 子命令（用户已确认此方案），
  而不是在 launch.sh 里重写一遍配置/服务逻辑 —— 避免双份真相。
- configure 分两阶段：先纯参数校验（不需要 root，失败返回 2，便于脚本/CI 提前发现），
  再 require_root → 写配置 → 写服务 → 启动。
- 完整性用 SHA256SUMS 清单 + 可跳过的 --no-verify；校验工具按 sha256sum → shasum → openssl 回退，
  不假定 `sha256sum -c --ignore-missing`（busybox 不一定支持），改为自行逐个比对哈希。
- launch.sh 不自我校验（先有鸡先有蛋），只校验它下载的 yjl-argo.sh 与 install.sh。

【资深研发】
新增/修改：
1. 新增 launch.sh
   - 自身开关：--ref / --repo / --source(离线) / --no-verify / --dry-run / -h|--help；
     支持 `--x V` 与 `--x=V` 两种写法；其余参数原样进 FORWARD 数组。
   - 流程：取件（curl 或 cp 本地）→ SHA256 校验 →（--dry-run 到此为止）→ root 检查 →
     复用 install.sh 安装 → FORWARD 为空则进 `yjl` 菜单，否则 `yjl configure $FORWARD`。
   - 缺 curl 时按 apt/apk 自动安装；staging 用 mktemp -d 并在退出时清理。
   - 打印配置步骤时不回显 FORWARD（避免把 Token 打进终端）。

【发现的问题】
1. 【安全·高】AGENTS.md 被 git 跟踪并已推送到公开仓库 xiaofeixoa/yjl-argo，
   文件内含明文服务器口令（口令原文已从本次记录中抹除，不再复现）。实测 raw.githubusercontent.com
   返回 200 且命中原口令。该文件是本地 AI 助手指令文件，不属于交付物，被误入库。
2. launch.sh 初版把 `ensure_curl` 放在 root 检查之后，非 root 且缺 curl 时无法先装 curl —— 已调整为先判断再下载。
3. Windows 侧 grep 的 `$'\r'` 判定不可靠（对纯 LF 文件也报命中），会误判换行符；
   改用 `tr -dc '\r' | wc -c` 与 `git ls-files --eol` 双确认：所有文件均为 LF，无 CRLF 污染。

【用户需求】
原文：「你把这台服务器的网络给我调优一下，加快速度，参考 ike-sh/bbrv3-lite 和 fscarmen/sing-box，
允许改内核、允许改所有参数，全都要。」
即：在第三轮那台真实 OVH 服务器（正在跑 yjl-argo + xboard-node，且用户已经在正常使用）上，
做尽可能激进的网络调优，包含换内核拿 BBRv3，并要求**不能把正在用的隧道弄断**。

【产品经理】
这是一台**无带外控制台**（只有串口 + 厂商救援模式）的远程生产机，且用户已在使用中。
因此必须把"用户想要的激进"与"远程机器不能砖"分开处理：
- 所有会中断连接/改变启动路径的动作，必须单独作为一道闸门，由用户确认后再执行；
- 每个阶段都要有**可一键回滚**的产物，并在此之前先做"能不能启动"的硬校验；
- 已经承诺"优化提速"，就必须给出**诚实的实测数字**，不能只贴配置文件。

【首席架构师】
- 参考仓库的调研结论先摆出来：
  * `ike-sh/bbrv3-lite`：核心思路正是 BBRv3 内核 + 少量 sysctl，且**刻意克制**（不碰 tcp_mem、
    不关网卡 offload、不动 RPS/RFS）。本方案与之一致。
  * `fscarmen/sing-box`：通读其 32 万字节脚本，**没有任何宿主机级 sysctl 调优块**，
    其 "bbr" 只出现在 TUIC 的 congestion_control 默认值里 —— 所以宿主机调优无可借鉴，如实记录。
- 分档执行，风险递增，每档独立可回滚：
  档 1（零风险，不重启）：BBR(v1) + fq + 18 项 sysctl + 1GB swapfile；
  档 2（需重启）：XanMod LTS 内核拿 BBRv3；
  档 3（激进项）：tcp_notsent_lowat / tcp_ecn / 大缓冲 —— 单独隔离测试，实测无益则退回默认。
- **明确不做**（附理由，写进配置文件注释里，避免后人反复"优化"）：
  * `net.ipv4.tcp_mem`：全局 TCP 内存安全阀，464MB 内存的机器动它才是真正的 OOM 风险；
  * 网卡 offload（GSO/GRO/TSO）：单核 virtio 下关闭只增加 CPU 开销，属伪优化；
  * RPS/RFS、IRQ 亲和：1 vCPU / 1 队列，无意义；
  * `tcp_adv_win_scale` / TIME_WAIT 类：无明确收益，保持内核默认。
- 缓冲预算按数据算而不是拍脑袋：2×BDP(@150ms) ≈ 19.9MB，RAM/32 保护上限 ≈ 14.5MB，取 **12MiB**。
- 内核选择：`linux-xanmod-lts-x64v2`(6.18.57) 而非 edge(7.2.11)；保留 Debian 原 6.12 内核可回退。
- 安全：XanMod 源强制用 **HTTPS**（官方文档给的是 http，属明文可被 MITM），
  并按 fingerprint 独立校验签名密钥后再信任。

   东京链路本身在两个时段波动 2–3 倍 —— **是时间漂移，不是算法优势**。
   改用"同链路严格交替 + 取中位数 + 多轮"后，优势缩到 +3.5% 以内。
   **教训：单次/非交替的跨时段对比在这类链路上不可信，必须交替执行。**
2. 【我的校验脚本误报】见上文"澄清一个我自己踩的坑"——把内置驱动当成缺失驱动，
   差点得出"内核不可启动"的错误结论。
3. 【激进项无收益】`tcp_ecn=1`（主动发起 ECN）实测零收益，却会让代理在"回源到我们
   无法控制的第三方"这条链路上承担中间设备兼容风险。
4. 【历史遗留·仍未解决】服务器公网口令此前已在公开仓库出现过，至今未更换（见下）。

【修复】
1. 把 `tcp_ecn` 从 1 **回归内核默认 2**（只对支持 ECN 的对端回应，不主动发起），
   并在 sysctl 文件里注明"如要重新开启改回 1 即可"。
2. 保留 `tcp_notsent_lowat=131072`：它面向的是**发送侧排队延迟**而非吞吐（Cloudflare 生产亦采用），
   且实测在 280ms 长 RTT 链路上未观察到吞吐被压制，故保留。
3. 把"实测结论"（BBR/cubic 无差异、缓冲无可测提升）**写进 `99-yjl-net.conf` 的注释头部**，
   让以后接手的人知道这些参数为什么在、以及别指望它们能"提速多少"。
4. 重写 sysctl 配置文件，使文件内容与**实际生效值完全一致**（此前 ecn 那行与实际不符）。
